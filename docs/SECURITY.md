# Security boundaries

Phase 1 runs entirely as the current user. It cannot back up unreadable root-owned data or prove complete-system recovery. No privileged helper, polkit rule, fstab edit, lingering or automatic deletion is installed.

Repository passwords are stored under Secret Service attributes `application=nyx-backup`, `account=DESTINATION_ID`, `kind=repository`. A Restic `--password-command` performs the lookup into a pipe. SMB credentials are stored with `kind=smb`. Each encrypted Rclone configuration has a random 256-bit unlock secret stored with `kind=rclone`; NAS passwords reach `rclone obscure -` through stdin. No password is put in argv, environment values, TOML, job state or logs. Inherited `RESTIC_*`/`RCLONE_*` variables are stripped from child commands to prevent backend/password overrides.

Rclone files use the standard `RCLONE_ENCRYPT_V0` format: SHA256(`[ASCII_RANDOM_PASSWORD][rclone-config]`) as the XSalsa20-Poly1305 key, with an independent 192-bit random nonce. Only cryptographic ciphertext and a hash binding it to the non-secret server/account settings reach disk. Changing the configured server, username or domain requires explicit credential setup before any connection; the app cannot silently use a previous encrypted target. The generated ASCII password avoids normalization ambiguity. Native Rclone decoding is part of the disposable fixture. Existing SMB configurations retain their unlock key during credential updates, so a failed Rclone/setup step does not strand existing ciphertext. Obscuring alone is not treated as encryption. Secrets are not guaranteed to be zeroized from process memory; same-user debuggers and a compromised desktop/keyring are outside this boundary.

Secret Service must be available/unlocked. Before password lookup, Backup searches Secret Service metadata and rejects locked credentials without requesting an unlock prompt. Failed lookup is a failed job; it never generates a replacement password or initializes a replacement repository. Recovery-password export is explicit, uses create-new semantics and mode 0600, and refuses to overwrite a file. Keep the export separately from both the computer and backup destination.

Local-folder destinations are intentionally unbound. For removable media use mounted destinations: exact mount point, filesystem type and mount source must match; block devices additionally require a matching filesystem UUID. A missing device cannot fall through into the bare mount directory. Repository paths containing parent-directory (`..`) components are rejected. Repository symlink escapes and nested mounts that differ from the bound mount are rejected before any write. NFS connection uses the exact existing user/users fstab definition and invokes unprivileged mount/umount; it never constructs system definitions. A physical unmount racing an operation remains possible; do not disconnect storage during a job. Application-managed NFS disconnect takes the worker lock.

SFTP supplies `BatchMode` and connection timeout to OpenSSH, retaining the user's host verification and authentication configuration. Connection testing requests the SFTP subsystem without requiring remote-shell permission. Unknown hosts must be approved outside Backup. SMB uses an app-owned encrypted Rclone config with a Secret Service unlock helper, without putting NAS passwords into repository URLs. Host/share/user metadata is ordinary configuration; it is not a secret value. Child diagnostics are suppressed rather than persisted because transports can include sensitive diagnostics. Failures retain exit status and actionable categories; this is less detailed than a native Restic diagnostic session.

Recognized private keys, secret stores and credential locations are outside defaults. Explicit profile authorization includes recognized credential paths in the encrypted backup. Files with arbitrary names can still contain secrets. Recognized database/container/VM stores remain excluded; SQLite headers catch some stores without filename extensions. Active WAL/process-descriptor/database markers block execution. Detection cannot prove application consistency, detect every store, or freeze a live filesystem. Stop applications or use proper exports. Metadata itself can reveal usernames, mount names and boot parameters and is included inside the encrypted snapshot.

Selection resolves source traversal/ancestor aliases before applying exclusions and active-store checks; absolute exclusion patterns also match the source spelling selected by the user. A selected symlink root, including a dangling link, is saved as a link and never traversed. Selection uses non-following directory traversal and passes NUL-separated paths through Restic's `--files-from-raw` stdin, avoiding shell interpolation and option injection. The selection may change between scan and execution. It is not a filesystem snapshot. Directory entries can change concurrently; encrypted backup authorization applies to the selected folders.

Retention requires explicit confirmation and is restricted to both Backup/profile tags. Snapshot IDs and tags are standard Restic metadata; a user deliberately editing tags can alter that scope. No automatic prune or unlock is run. The integration D-Bus API rejects unapproved profiles and all initialization, deletion, mutation, restore, credential retrieval and arbitrary-command requests. Explicit local GUI/CLI administration uses a separate private Unix socket with kernel UID verification, strict operation allowlisting, exact-profile retention confirmation, configuration-path matching, bounded requests and read/write timeouts. Its operations run in the same daemon and are not exposed as D-Bus integration methods. UID checks do not grant trust to external/remote callers. Any future Core Control integration must preserve these receiving-app checks.

References: [Restic password-command](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), [Rclone SMB](https://rclone.org/smb/), [Rclone encryption](https://rclone.org/docs/#configuration-encryption).

## Phase 2 restoration

Restoration remains an explicit local operation; no restore method is added to the integration D-Bus API. The existing private UID-checked administration channel accepts typed restore requests bound to the same configuration context. Apply and rollback require the exact reviewed plan ID. Snapshots must have exact IDs and both Backup/profile tags; receipts must belong to the requested profile. Restoring into the filesystem root is refused.

Selected contents are decrypted and verified in a private plan directory before applying. This is authorized plaintext staging for restoration, not an automatic recovery-password export. Diff contents return only to the requesting local client; job journals and diagnostics contain metadata and fingerprints, not restored text. Staging and recovery copies are retained, including after interruption. Provide disk space for staging, new target versions and saved originals.

File writes use directory descriptors with no-follow access and no-replace renames. Current fingerprints are checked before applying and again during replacement. Originals are moved to retained paths before the new file is installed; the intent is synced before mutations. Rollback checks current and saved fingerprints and preserves conflicting data. There is no filesystem-wide transaction or guarantee against every concurrent directory rename or storage failure. The tests cover an interrupted original-file move through a persisted journal, not a host power-loss recovery.

Quick Dotfiles Restore is limited to current home/configuration paths, requires explicit authorization for recognized credentials, and excludes recognized databases/VM/container stores and SQLite data. Backup's own working paths and configured repositories are protected. Apps with in-memory edits must be closed first; filesystem checks cannot detect every unsaved change. Ordinary contents, symlinks, modes and mtime are applied; ownership, ACLs, xattrs and hard-link topology are not. No complete-system, cross-PC, privileged or boot recovery claim is introduced. See RESTORE.md.


## Phase 3 migration and Setup

Migration source metadata must belong to the exact profile snapshot. Explicit external inventories are marked unattested. Roots map only into the actual current user's home/config; sensitive stores, hardware-specific files and Backup state remain protected. Prepared adaptations use the same staged diff, confirmation, no-follow replacement and rollback boundaries as Phase 2. Unknown configuration can contain secrets or executable behavior, so review is required.

Setup bundles contain private metadata and target binding, no repository passwords or arbitrary command fields. The SHA-256 consistency digest is not authentication. The installed consumer recomputes target and package eligibility before application, validates package names, and uses a fixed sudo/pacman argument array with ordinary interactive authorization. Foreign builds, recognized hardware packages and Flatpak remotes are never executed from source metadata. Classification is heuristic. No root helper, repository refresh, integration installer or new destructive D-Bus method is supplied. See MIGRATION.md for format and target-bound handoff limits.


## Phase 4 offline recovery

The root-run recovery tool is a separate executable with no daemon, setuid bit, polkit grant or service API. Apart from inventory, commands require root, the recovery environment file and `nyx.recovery=1` kernel parameter. These are accident-prevention checks, not protection from a malicious root process. GTK exposes only boot-kit generation. The kit copies installed executable/kernel/library files, never user sources, keyrings or profile secrets; it is unsigned and must be treated as a trusted recovery OS once booted.

Capture authorizes every source byte, including unallocated regions, credentials and deleted remnants. It requires a read-only whole disk, rejects active mounts/holders/swap and uses exclusive block opens. A full private plaintext scratch image is required. Passwords enter via terminal/pipe and are passed on fresh inherited descriptors; they never appear in argv, environment, manifests or ordinary files. Existing repository validation failure never initializes another repository.

Restore targets must match the source's disk and sector size. Full image verification and target fingerprints precede the first write; exact confirmation and repeated identity checks protect the reviewed selection. Before overwriting, a synced plan is marked `applying`; only a full synced write and reread hash produce `verified`. Interrupted writes can leave a partial disk and cannot roll back. Another root process or storage failure can defeat software assumptions; physical-machine and power-loss behavior remain unqualified. Duplicate disk/filesystem UUIDs are intentionally preserved. See RECOVERY.md.
